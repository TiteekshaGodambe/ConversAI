# Evaluating ConversAI

Three ways to evaluate, from fastest to most thorough:

| Option | What you need | Time |
|---|---|---|
| A. Live test in VS Code | VS Code + GitHub Copilot (agent mode) | ~10 min |
| B. Smoke test without an LLM | Python 3.11+ | ~2 min |
| C. Reproduce the benchmark offline | Python 3.11+ | ~10 min |

**Live endpoint:** `https://conversai-mcp-w73zfflpqq-uc.a.run.app/mcp` (MCP over streamable HTTP, Google Cloud Run,
us-central1). No login is required during the evaluation. The service scales to zero, so the **first request after
an idle period can take about 30 seconds**.

---

## A. Live test in VS Code

1. Clone this repository and open the folder in **VS Code** (recent version) with **GitHub Copilot** signed in.
   `.vscode/mcp.json` already registers the server:
   ```json
   { "servers": { "conversai-cloud": { "type": "http", "url": "https://conversai-mcp-w73zfflpqq-uc.a.run.app/mcp" } } }
   ```
   (Without cloning: create `.vscode/mcp.json` with the content above in any folder.)
2. Open **Copilot Chat** and send any message once (VS Code starts MCP servers when a chat session exists).
3. `Ctrl+Shift+P` → **MCP: List Servers** → **conversai-cloud** → **Start**. It should show **Running** with 18 tools.
4. Start a **new chat** and select the **ConversAI-Cloud** agent in the agent dropdown (from `.github/agents/`).
   It only allows the ConversAI tools. Alternatively choose **Agent** mode and, in the tools picker, enable only
   `conversai-cloud`.
5. Choose a specific model rather than **Auto**.
6. Every query opens an **approval dialog**: read the *Meaning*, the generated SQL and the BigQuery *Estimate*, then
   approve. If a "Run in terminal?" prompt ever appears, choose **Skip**: everything runs through the MCP tools.

### Test script: one data-pull request, end to end

Ask these **in order, in one chat** (the export in step S2 pins the conversation to the extract).
Expected answers come from the seeded demo dataset.

**Analyst: scope the request (full data)**

| # | Ask | Expected |
|---|---|---|
| A1 | How many paper-statement accounts do we have, and what is their total balance? | 2,050 accounts; $6,498,372.86 |
| A2 | How is the 30+ day delinquency rate defined? | Active accounts 30+ days past due ÷ active accounts (charged-off excluded), from the semantic layer |

**Stakeholder: answer, extract, follow-ups**

| # | Ask | Expected |
|---|---|---|
| S1 | What is the 30+ day delinquency rate and total payments for paper-statement accounts from July to September 2026? | 1.33%; $4,256,193.46 |
| S2 | Export this data so we can analyse it further. | Export approval dialog; extract created in BigQuery (~2,033 accounts, 6,096 billing cycles); the chat now runs on the extract |
| F1 | How did that rate move month by month? | Jul 1.48%, Aug 0.99%, Sep 1.33% (notes say it ran on the extract) |
| F2 | Break it down by bureau score band for September. | <580: 13.95% · 580-669: 1.75% · 670-739: 0% · 740+: 0% |
| F3 | How does this compare with paperless accounts? | "Outside the export" warning: the extract holds paper-statement accounts only |

**Analyst: deeper analysis on the extract**

| # | Ask | Expected |
|---|---|---|
| A3 | Of the accounts that were current in August, what share rolled to 30+ days past due in September? | 1.05% |
| A4 | What is the payment rate by utilization band for the quarter? | <30%: 64.79% · 30-80%: 23.03% · >80%: 3.20% |

**Governance (start a new chat)**

| # | Ask | Expected |
|---|---|---|
| G1 | How many accounts had their behavior score improve last month while their delinquency did not improve? | 2,351 accounts |
| G2 | How many accounts had their bureau score drop by 50 points or more last month? | No governed definition exists: the agent proposes one; the dialog shows the meaning, the server's checks (whitelist, MetricFlow compile, BigQuery check) and the YAML. After approval: 2 accounts, labelled PROVISIONAL |
| G3 | What is our profit? | Declined: no governed profit metric; the agent does not guess |

### What to look for

* The agent never writes SQL: the SQL in each dialog is generated by the server from the semantic layer.
* The same definition is applied every time (ask S1 again in another chat: identical result).
* Cost is shown before execution (BigQuery dry run), and nothing runs without approval.
* Follow-ups after an export run on the extract, and questions outside its scope are flagged.

## B. Smoke test without an LLM

```bash
pip install "mcp>=1.12,<2"
python deploy/check_cloud.py --url https://conversai-mcp-w73zfflpqq-uc.a.run.app/mcp
```

Expected: every line `OK`, including *this is the CLOUD server* (targets `bigquery`, `gcs_lake`), a BigQuery dry run,
the extract list and the proposed-definitions log on Cloud Storage, and a test definition passing the server's
checks (the script declines the approval, so nothing is saved).

## C. Reproduce the benchmark offline

```bash
python -m venv .venv
.venv\Scripts\activate             # macOS / Linux: source .venv/bin/activate
pip install -r requirements.txt pytest
python tables/build_tables.py      # regenerates the exact demo dataset (fixed seed)
python eval/run_eval.py            # 54 passed: every gold question vs independent hand-written SQL, on 2 engines
python -m pytest -q tests          # 48 passed: engines agree, extracts, proposed definitions, BigQuery / GCS paths
```

`eval/gold.yaml` holds, for each question, the governed semantic query and an independent hand-written SQL check.
`eval/run_eval.py --llm` (needs `ANTHROPIC_API_KEY`) also measures natural-language-to-semantic-query accuracy.

## Notes for evaluators

* The data is synthetic; no personal or customer data is used.
* Public demo mode: deleting extracts is disabled; extracts expire automatically after 7 days.
* One Cloud Run instance serves all evaluators; conversations are kept separate.
* Contact the team if the endpoint is unavailable; it can be redeployed with `deploy/gcp_deploy.cmd` and
  `deploy/make_public.cmd`.
